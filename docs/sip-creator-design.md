# SIP Creator design

SIP Creator is a Go library and CLI that assembles a producer's essence files and descriptive metadata into a standards-conformant Submission Information Package (SIP). It reads an input folder, copies the essence into the package layout (computing fixity natively during the copy), optionally enriches files with format info from a pre-computed characterization report (a `siegfried.json` sidecar), and generates the descriptive, preservation, and structural XML that describe the content and tie the package together. The output targets are a [Meemoo SIP v1.2](https://developer.meemoo.be/docs/diginstroom/sip/1.2/) `basic` package (the stable Meemoo spec; 2.0/2.1 are release candidates) layered on the [E-ARK](https://earksip.dilcis.eu/) profile, and a plain E-ARK SIP for RODA-class repositories with Simple Dublin Core (`eark` profile) or [MODS 3.7](https://www.loc.gov/standards/mods/) (`eark-mods` profile) as its descriptive metadata. The BagIt envelope Meemoo's transfer requires is deliberately out of scope ([ADR-0008](decisions/0008-bag-layer-out-of-scope.md)): bag the package directory with a reference BagIt implementation.

This document describes **what the system is today**: the domain model, the package layout it produces, and the build lifecycle. It reflects the code as it stands, including its known gaps and rough edges; where the code is mid-evolution, that is called out rather than smoothed over. The *why* behind key choices lives in the [decision records](decisions/); planned changes live in [plans/](plans/); the backlog lives in [TODO.md](TODO.md). See [README.md](README.md) for how the docs are organized, and the repo-root `CLAUDE.md` for coding conventions.

> **Status: experimental, work in progress.** Three profiles are registered: `basic` (Meemoo SIP 1.2), `eark` (plain E-ARK SIP with Simple Dublin Core) and `eark-mods` (the same with MODS 3.7). All three sample packages validate **VALID** with zero warnings against commons-ip, each against the E-ARK spec version of its era (`basic` 2.0.4; `eark` and `eark-mods` 2.2.0), and every `mods.xml` in an `eark-mods` package validates against the MODS 3.7 schema with xmllint (the [descriptive-model plan](archive/descriptive-model.md), shipped 2026-10-01).

## Domain model

The domain lives in the `sip/` package as a graph of plain structs, built entirely in memory before anything is written to disk. It mirrors the OAIS/METS vocabulary: an intellectual entity, its representations, and the files within them.

- **Package** (`sip.Package`): the unit of work, one SIP. Carries its `Identifier` and `Location` (the on-disk package directory), a single root `Entity`, and the generated top-level files (package `MetsFile`, package `PremisFile`, `SchemaFiles`). Created by `NewPackage(baseDir, identifier)`, which reuses a non-empty identifier (an update keeps the original's `mets/@OBJID`), mints one otherwise, and sets `Location = baseDir/<identifier>`.
- **Entity** (`sip.Entity`): the intellectual entity being preserved (the "what this is"). Holds its `Identifier`, a map of `AdditionalIdentifiers` (e.g. `MEEMOO-LOCAL-ID`), its `Representations`, its `Description` (the decoded descriptive metadata behind the `sip.Description` interface, `meemoo.Terms`, `eark.Terms` or `earkmods.Record`, awaiting serialization by the writer, or a `build.EncodedDescription`, a finished document supplied as a file that the eark profiles copy as it is), its `DescriptionFile` (the descriptive-metadata file node). A package has one root entity; sub-entities are not modeled (an open question in [TODO.md](TODO.md)).
- **Representation** (`sip.Representation`): a typed grouping of the essence (e.g. a master vs. a derivative). Holds its `Name` (the package-side directory name under `representations/`, taken verbatim from the producer's name), its `Label` (the display name, emitted as the representation METS `mets/@LABEL`), `Identifier`, its `Files`, its optional `Description` and `DescriptionFile` (a description of this version only), its own representation-level `MetsFile` and `PremisFile`, its own METS `Declaration` (set by the assembler: the profile declaration, or, when the definition sets `EmitRepresentationType` as both eark profiles do, a copy that types the representation by its resolved type in both the `TYPE` and `CONTENTINFORMATIONTYPE` attribute pairs so ingest systems show it as the representation's type; [ADR-0013](decisions/0013-representation-type-from-label.md)), and a back-reference to its `Entity`. The producer supplies name, label, and type on `build.SourceRepresentation`; label and type are optional and resolve along the name → label → type cascade in the assembler.
- **File** (`sip.File`): one file in the package, whether essence or generated metadata. Records `Identifier`, `Name`, `Checksum` (MD5), `Size`, `Created` (RFC3339Nano), `Path`, `Source` (the absolute input path an essence file is copied from; empty for generated metadata), `Mime`, and, for essence, a `Format`. `Path` is the href **relative to the METS document that references the file**: essence and representation PREMIS are representation-relative, schema/descriptive files and representation METS entries are package-relative. `Mime` is what METS `@MIMETYPE` declares (a CSIP MUST) and is never empty by write time and never a guess: the characterization report's assertion for essence/documentation, a type true by construction for generated XML (`text/xml`) and bundled XSDs (`application/xml`), or `application/octet-stream` as the admitted unknown. The assembler declares `Path` and `Mime` up front; the writer back-fills `Checksum`/`Size`/`Created` as each file lands on disk.
- **Format** / **FormatRegistry** (`sip.Format`, `sip.FormatRegistry`): the characterization result attached to an essence file: a `FormatRegistry` naming the registry (`PRONOM`) and the format's key in it (e.g. `fmt/43`) from the Siegfried report, plus a `Role` of `specification`. Nil when no report is supplied or the report recorded no match ([ADR-0009](decisions/0009-characterization-as-sidecar-input.md)); the PREMIS template omits `premis:format` accordingly.
- **Identifier validation** (`sip.ValidateIdentifier`): there is no identifier type; every struct above carries its identifier as a plain `string` in the `uuid-<uuid>` form, and `ValidateIdentifier` checks that form (the prefix keeps a UUID valid as an xsd:ID, which may not start with a digit).
- **Record status** (`sip.RecordStatus`): metsHdr/@RECORDSTATUS as a typed string carrying the six SIP3 values as constants (`RecordStatusNew` through `RecordStatusDelete`). `ParseRecordStatus` maps text in any case onto the vocabulary, `IsValid` checks a value exactly (the template renders it as is), and `IsUpdate` says whether the status references an earlier package, whose identifier the source package must then supply. It is the one typed METS vocabulary: SIP3's list is closed, where the CSIP content category is open-ended and stays a string.
- **Event** (`sip.Event`): an empty stub. PREMIS events are not modeled yet.

**All identifiers take the form `uuid-<uuid>`** and are minted locally with the standard library `uuid` package. SIP Creator asserts no authority over these identifiers; they are meaningful only within the package (see [ADR-0001](decisions/0001-package-builder-not-archive.md)).

## Package layout

The `basic` profile produces this on-disk tree under `Location` (`dest/uuid-<uuid>/`):

```
uuid-<uuid>/
  METS.xml                              package-level structural map
  metadata/
    descriptive/
      dc+schema.xml                     descriptive metadata (Dublin Core + schema.org; dc.xml, Simple DC, in the eark profile; mods.xml, MODS 3.7, in the eark-mods profile)
    preservation/
      premis.xml                        package-level PREMIS (the intellectual entity)
  representations/
    <name>/                             one directory per representation, named by the representation's Name
      METS.xml                          representation-level structural map
      data/
        <essence files>                 the copied content
      metadata/
        preservation/
          premis.xml                    representation-level PREMIS (representation + its files)
  schemas/
    *.xsd                               the XSDs the package's documents point at, copied verbatim from the bundle
  documentation/
    ...                                 optional: copied from the input's documentation/ folder
```

The two eark profiles produce the same tree without the `premis.xml` files at either level (their choice for RODA, see the CLI/library boundary below). A descriptive document the producer supplied as a file (`dc.xml`, `mods.xml`) lands at the same path as a generated one, copied as it is.

The CLI then zips the whole tree **uncompressed** (`zip.Store`) to `dest/uuid-<uuid>.zip`, unless `--no-zip` is given. Under the eark profiles the zip is the deliverable; under `basic` the deliverable is the package directory wrapped in a BagIt bag, which this tool does not produce.

### The metadata model

The descriptive side is built around four concepts ([ADR-0024](decisions/0024-the-metadata-model.md)). A profile has a **metadata model**; a **description** is an instance of it; a description is written as an XML document in the model's **document format**, or supplied as **terms** in a description.csv.

- **Metadata model** (`build.MetadataModel`, on `Definition.Model`): what the tool knows about one kind of description: the description type that holds it (`ValidateType`), how it is written as a document (`Encode`), the XSDs that document points at (`Schemas`), and how the METS dmdSec types the document (`ModelType`, `ModelTypeVersion`). There are three: Meemoo's dc+schema.org, Simple Dublin Core and MODS 3.7. The fields and their rules live on the description type, not on the interface.
- **Description** (`sip.Description`): one instance of a model, the description of one intellectual entity or representation: `meemoo.Terms`, `eark.Terms`, `earkmods.Record`, or `build.EncodedDescription`, a finished document supplied as a file.
- **Document format**: the root element, namespace and version that make an XML file a document in the model, and the file's name (`Definition.DocumentName`, a convention of the profile). `build.DocumentFormat` is the optional part of a model that accepts a supplied document; Meemoo's model has a document format but does not implement it, because its document must carry the identifier the build mints.
- **Term** (`sip.Term`): one key, an optional language and a value. In a description the key is the element's name as the standard spells it (`dcterms:title` for Meemoo, `title` for Simple Dublin Core); in a description.csv it is the CSV's key, which the profile's mapping in `cli/input/mapping` turns into the element. The library speaks the standard's names; the CLI owns the CSV's keys.

"Model" means the data model only; `sip/` is the domain model.

### The three metadata standards

Each metadata file corresponds to one preservation standard, generated by its own package: the profile's for the descriptive document, an encoder's for PREMIS and METS:

- **Descriptive**: `metadata/descriptive/dc+schema.xml`, Dublin Core terms + schema.org in the Meemoo `1.2/basic` namespace (basic profile), a simple-DC document (eark profile), or a MODS 3.7 document (eark-mods profile). Three descriptive standards ([ADR-0015](decisions/0015-descriptive-worlds-dc-and-mods.md)), each inside its profile's own package ([ADR-0018](decisions/0018-engine-and-profile-packages.md)): `profiles/meemoo` for the Meemoo document, `profiles/eark` for Simple Dublin Core, `profiles/earkmods` for MODS. The model follows its standard ([ADR-0021](decisions/0021-descriptive-model-follows-its-standard.md)): the two DC documents are flat lists, so their description types (`meemoo.Terms`, `eark.Terms`) are lists of one term shape, `sip.Term` (the element's name in the model, a language tag, a value), each with its own table, rules and template; MODS is a tree, so `earkmods.Record` is a struct typed by field. The Meemoo model is **one closed table of elements** ([ADR-0011](decisions/0011-closed-descriptive-vocabulary.md), `meemoo/elements.go`): a row per element, named as Meemoo's specification names it (`dcterms:isPartOf`, `schema:artMedium`), carrying Meemoo's cardinality limit (many / once / once per language) and the `xsi:type`. `meemoo.Terms` is keyed by those names. Validation (an unknown element, the cardinality limits and the Dutch-language rule in `Terms.Validate`) and the template (the element name, EDTF typing) both read the table. The CSV's keys (`ispartof`, `artmedium`) are the CLI's: `cli/input/mapping` maps each onto its element, as it maps the MODS keys onto the record's fields; the library speaks the standard's names for all three profiles. What a package-level description must state is the standard's list (`required`: the identifier, title, description and created elements for Meemoo's basic profile), checked by `ValidateRequired` in `SourcePackage.Validate` and by `check`; a representation's description is exempt. A new element is a table row, a key in the CLI's mapping and an input-spec §3 line. Simple Dublin Core is the fifteen DCMES elements as keys, optional and repeatable, unqualified in the document; there is no dumb-down from Meemoo's model into it. The MODS model describes one bibliographic record: `earkmods.Record` holds its `Identifier` (a `mods:identifier` with a fixed `type`), its `Titles` (one `mods:titleInfo/mods:title` each, with `xml:lang`) and its `Items`, the record's physical copies, each a call number with an optional barcode (unique across the items) and an optional volume or issue designation, rendered as one `location/holdingSimple` with a `copyInformation` per item. The template walks the fields in a fixed order; the profile package holds no key table, because the CSV keys that fill the fields are the CLI's (`cli/input/mapping`), so a further MODS element is a field on the record, a template line, a key in the CLI's mapping and an input-spec line. Items describe the package level only: a copy is never a representation ([ADR-0015](decisions/0015-descriptive-worlds-dc-and-mods.md)). A finished document supplied as a file, `build.EncodedDescription`, is a fourth description type for the two eark profiles ([ADR-0021](decisions/0021-descriptive-model-follows-its-standard.md)): the engine reads its root element once and the profile's metadata model, through the optional `build.DocumentFormat` interface (the idiom `IdentifierSwapper` set) and its `ValidateDocumentRoot`, says whether that root is a document in its format (`simpledc` without namespace for `eark`; `mods:mods` in the MODS v3 namespace declaring `version="3.7"` for `eark-mods`); the writer copies the file as it is with the store's streamed copy, fixity computed on the way as for essence, its own schema-location hint included. The assembler does not branch and the metadata models never see a document. The `basic` profile's model does not implement `DocumentFormat`, because Meemoo's document needs the identifier swap, so the engine refuses a document for it. Validity against the schema stays with the validators downstream ([ADR-0003](decisions/0003-validation-stays-external.md)).
- **Preservation**: `premis.xml` at both package and representation level ([PREMIS](https://www.loc.gov/standards/premis/) 3.0): the objectIdentifiers, fixity, format registry, and the structural relationships (`represents`, `is represented by`, `includes`, `is included in`) between entity, representation, and files. Unlike the METS and descriptive documents, the PREMIS documents point `xsi:schemaLocation` at the remote `https://www.loc.gov/standards/premis/premis.xsd`, and the package ships no PREMIS schema: Meemoo SIP 1.2 requires exactly that value when the attribute is used, and only the Meemoo profile writes PREMIS. Encoder: `encoders/premis`.
- **Structural**: `METS.xml` at both package and representation level ([METS](https://www.loc.gov/standards/mets/)): the manifest tying descriptive and preservation metadata, the file inventory (with checksums/sizes), and the structMap together. The package METS points at each representation METS via `mptr`. Encoder: `encoders/mets`.

## Build lifecycle

Entry point: `main.go` → `cli/cli.go` → `cli/create_cmd.go`. The command is:

```
sip-creator create [src] [dest] --profile basic
```

`create_cmd.go` resolves `--profile` against the profile registry (`profiles.Get`); an unknown or empty value returns an error listing the available profiles (`profiles.Names`). It resolves the run flags (`--status`/`--updates` per SIP3, `--content-category` over `SIP_CONTENT_CATEGORY` over the registry value) onto the source package's `RecordStatus`, `PackageIdentifier` and `ContentCategory`, reads and validates the input folder with the profile's mapper and document spec (`input.Read(root, mapper, documentSpec)`: the `input.Mapper` that maps the rows of `description.csv` onto the profile's description, resolved next to the definition by `cli/profile.go` from its table of mappers, and the `input.DocumentSpec` built from the definition's `DocumentName` and `Model`; all violations reported at once, the result the `build.SourcePackage` the builder takes), and calls `Build(source)` on a builder constructed for the profile with `build.New`. On success it zips the assembled `*sip.Package` with the `archive` package (`archive.New(config).Zip(pkg)`), unless `--no-zip` is given. The sibling `check` command runs the same read alone, with the same `--profile` and no configuration, then the profile's rules on the source package it read (`Definition.ValidateSource`, which `Build` runs too): structure and metadata validation, no build.

The three profiles in this repository build the same kind of package, an E-ARK SIP; what sets them apart is the descriptive model and the context it serves. `eark` describes an intellectual entity in Simple Dublin Core, in general terms that any E-ARK repository can read. `eark-mods` describes it in MODS 3.7, for library material whose description most likely comes from a MARC 21 catalogue record. `basic` adds Meemoo SIP 1.2's rules on top of E-ARK and describes the entity in Meemoo's own model, a mix of Dublin Core terms and schema.org that matches how Meemoo describes material in its archive and on its dissemination platform. Why the descriptive standard sits on the profile is recorded in [ADR-0015](decisions/0015-descriptive-worlds-dc-and-mods.md).

A profile is **data, not code**: a `build.Definition`, built by the profile's own package under `profiles/` and resolved by name from the registry in `profiles/`, carrying its metadata model, the file name of its descriptive document, emission flags, its rules on representations (`MaxRepresentations`, `AllowRepresentationDescriptions`: Meemoo's basic profile allows one representation and no description below the package level, checked by `Definition.ValidateSource`), and the `sip.MetsDeclaration` METS values: profile URL, content typing, record status, agents. One agent is deliberately *not* registry data: the submitting ORGANIZATION is operator identity, supplied per deployment. `Definition.WithSubmitter(name, orID)` returns a completed copy, and profiles with `RequireSubmitterORID` set (Meemoo's) refuse to build without the OR-id (the CLI reads both from `SIP_SUBMITTER_*`; embedding systems pass them as arguments). The **descriptive standard** is the one behavioral choice a profile makes: its metadata model, an implementation of `build.MetadataModel` that the profile package supplies (Meemoo's dc+schema.org, Simple DC, MODS 3.7): a check that the input's descriptions have the model's type (`ValidateType`), run before anything else; whether the entity identifier is swapped into the document (Meemoo's model does, the two eark models never, [ADR-0012](decisions/0012-eark-keeps-producer-identifier.md)); `Encode`, which writes the document; and `ModelType` and `ModelTypeVersion`, which the assembler sets on each descriptive file node (`sip.File.MDType` and `MDTypeVersion`, read by the dmdSec's mdRef), so the METS cannot label the document as another model's. Everything that needs the concrete terms type lives in the profile package; the engine imports no profile ([ADR-0018](decisions/0018-engine-and-profile-packages.md)). All profiles share the one canonical writer; every other difference is a value. See [ADR-0007](decisions/0007-profile-families-share-one-writer.md) for the one-writer rule and its fork triggers, and [ADR-0015](decisions/0015-descriptive-worlds-dc-and-mods.md) for why the standard sits on the profile rather than behind a family constant. One engine reads it: `build.New` takes the profile definition with the destination and logger (`build.Config`) and refuses a profile without a metadata model, and `Builder.Build(source)` takes a per-build `build.SourcePackage`, the package as it is handed to the build, as data (descriptive terms, representations as labeled source-file lists, documentation, received PREMIS, an optional characterization report, and the values that are the package's own: the identifier of the package it updates, its record status, its content category, the profile supplying the defaults). The build runs in **two strictly separated phases**: validate the input and assemble the complete package graph in memory, then emit it to disk. Errors are returned, not panicked, and failures before the write phase leave no partial package directory behind. Adding a Meemoo content profile (material-artwork, newspaper, …) is a definition in a profile package plus one registry line, not a new build path.

**Phase 1: assemble** (`build/assemble.go`, zero writes; before it run the check of every description (the metadata model's `ValidateType` of a description's type; for a supplied document the engine reads the root element and the profile's `DocumentFormat` validates it) and `SourcePackage.Validate`):

1. Mint the package (`sip.NewPackage`; an identifier set on the source package is reused, which is how an update keeps the original `mets/@OBJID`) and the root `Entity`.
2. Take the descriptive terms from the input. When the standard swaps (Meemoo's), replace the producer's `identifier` term with the entity's UUID and lift the producer's value onto the entity as `MEEMOO-LOCAL-ID`; the Simple DC standard has no swap, so `dc.xml` keeps the producer's identifier ([ADR-0012](decisions/0012-eark-keeps-producer-identifier.md)). Park the terms on the entity (`Entity.Description`) for the writer to serialize. The descriptive `File` node is declared with the profile's `DocumentName`.
3. Declare one schema `File` node per XSD the package's documents point at: the METS encoder's list (`mets.Schemas`) plus the metadata model's (`Schemas()` on `build.MetadataModel`), in sorted order (deterministic METS emission), each name once. Nothing else ships: an XSD no document references is noise. A name the bundle does not hold fails assembly before any write.
4. Turn each supplied representation into a graph node (the producer's name, unique and already validated, becomes the package-side name verbatim; the label and type resolve along the name → label → type cascade) and, when a characterization report is present, enrich each essence file from the report's record for the **source file** ([ADR-0009](decisions/0009-characterization-as-sidecar-input.md)): no report is skipped; a present report is strict (missing essence entry, per-entry sf error, missing checksum, or an MD5 mismatch against the source bytes aborts assembly); a recorded no-match leaves that file's `Format` nil. Documentation files (package and representation level) need no entry but are checksum-verified when one exists. Received PREMIS files are checked to be well-formed `premis:premis` documents and declared as nodes, never parsed.
5. Declare the generated-metadata `File` nodes: per representation a `premis.xml` (only when the definition's `EmitRepresentationPremis` says so) and its `METS.xml`, plus the package `premis.xml` (per `EmitPackagePremis`) and the package `METS.xml`. Assembly leaves the graph complete: the writer creates no nodes, it only emits what the graph declares and back-fills fixity.

**Phase 2: write** (`build/write.go`, backed by the `store/` package), in a dependency order encoded exactly once, top to bottom in `write()`. The order is a hard constraint, not style: later files embed the fixity of earlier ones, so reordering emits METS documents whose checksum references are wrong (see "Ordering dependencies" below):

6. Skeleton directories.
7. Schema files and package documentation copies (package METS references their fixity).
8. Per representation: directories, then essence copies. Fixity is computed during the streamed copy and back-filled onto the graph nodes, so it describes the bytes actually in the package.
9. Package descriptive XML (serialized from `Entity.Description` by the profile's metadata model, or copied as it is through the store's streamed copy when the description is a supplied document).
10. Per representation: its descriptive XML (when the representation carries a description), the generated `premis.xml`, documentation copies, received PREMIS copies, then `METS.xml`; the representation METS embeds the fixity of all of them. Whether a generated PREMIS node exists was decided at assembly by the emission flags, and the METS templates render their references conditionally, so a profile without PREMIS stays valid.
11. Package `premis.xml` (the intellectual entity) and the package-level received PREMIS copies.
12. Package `METS.xml`, **strictly last**, because it references every representation METS, all preservation and descriptive documents, and every schema and documentation file by checksum.

`Build` returns the assembled package; zipping is the caller's step (the CLI's, above).

### Ordering dependencies

The dependency order is still not enforced by types, but it now lives in exactly one place (the numbered steps of `write()`) instead of being re-hand-sequenced per profile:

- Characterization enrichment (when a report is present) happens at assembly, **before** any PREMIS is rendered (PREMIS records the format registry).
- Representation PREMIS is written **before** its representation METS (which embeds its fixity).
- Everything is written **before** the package METS; it is always **last**.

## Code organization

Layered by responsibility. The `sip/` graph is the shared domain; everything else reads or writes it.

- **`sip/`**: the domain model (above). Plain structs and constructors, no IO.
- **`build/`**: the engine, profile-driven package building split into the assemble and emit phases. `definition.go` holds `Definition` (a profile as data) and `model.go` the `MetadataModel` interface a profile plugs in (with the optional `IdentifierSwapper` and `DocumentFormat`); `source.go` holds `SourcePackage` and its `Validate`; `document.go` holds `EncodedDescription`, a supplied descriptive document as a description type; `builder.go` holds `Config`, the `Builder` engine and `Build(source)`; `assemble.go` is the pure source-to-graph phase; `write.go` is the canonical emission order. The engine imports no profile. Covered by an external test package (`build_test`, with `export_test.go` exposing the assembly phase) building with the real profiles: graph shape, walk edge cases, the guarantee that assembly writes nothing to disk, definition-driven behavior.
- **`profiles/`**: the registry (`Get`/`Names`) over one package per profile ([ADR-0018](decisions/0018-engine-and-profile-packages.md)). `profiles/meemoo` is the `basic` profile, `profiles/eark` the `eark` profile and `profiles/earkmods` the `eark-mods` profile: each holds its description type, key table (Meemoo, eark), validation, template and the XSDs its document points at, and exports one `Definition` with an unexported type implementing `build.MetadataModel`. Everything that needs the concrete description type lives here.
- **`store/`**: dumb filesystem primitives rooted at the package directory (`MkdirAll`, `CopyFile`, `WriteMetadata`). Callers deal only in package-relative paths; writes truncate (safe re-runs); `CopyFile` computes MD5/size in the same streamed pass as the copy; `WriteMetadata` renders to memory first, so a failed template leaves no partial file.
- **`encoders/`**: the renderers of the graph, `mets` and `premis`, each a thin `Encode*(io.Writer, …)` API backed by a `text/template`; every profile difference reaches them as data. **No XML library**: all XML is generated from templates (see [ADR-0002](decisions/0002-xml-via-text-template.md)). METS elements that describe a graph node (`file`, `dmdSec`, `digiprovMD`, the per-representation `fileGrp`) carry that node's identifier, so METS and PREMIS agree on file identity; element IDs with no graph counterpart (`fileSec`, `structMap` divs, the data/documentation/schema `fileGrp`s) are minted per render by the mets encoder's `identifier()`. `mets` exports `Schemas`, the bundled XSDs its documents point at; the received-PREMIS check lives next to the PREMIS template. `xmldoc` is the one XML reader the tool has: the root element of a well-formed document, shared by the received-PREMIS check and by `build.EncodedDescription`.
- **`characterization/`**: decodes pre-computed characterization reports into per-file records (`DecodeSiegfried(io.Reader) (Report, error)`; `Report` maps input-relative slash paths to `Record`s carrying format, mime, MD5, and per-file tool errors). Decoding carries facts without judging them; strictness policy lives in the assembler, which knows which entries it needs ([ADR-0009](decisions/0009-characterization-as-sidecar-input.md)). A future FITS/DROID sidecar is one new decode function.
- **`schemas/`**: all XSDs bundled via `//go:embed`; `Get()` returns them as `map[name][]byte`. Which of them a package ships follows from its documents: `mets.Schemas` plus what the profile's metadata model reports through `Schemas()` (the XSDs its document points at and their relative imports); the assembler ships each name once and nothing more. The bundle is the union of what the profiles ship: the basic profile ships the METS set plus Meemoo's descriptive schema and the Dublin Core family it imports; the eark profile ships the METS set plus `dc.xsd`; the eark-mods profile the METS set plus `mods-3-7.xsd`, whose own imports are absolute loc.gov URLs, so nothing else ships for it.
- **`archive/`**: `Zip` walks the package directory and writes an uncompressed zip.
- **`cli/`**: the operator frontend. Cobra commands, env config (`.env` via godotenv, parsed with caarlos0/env; `CONFIG.md` is generated from the config struct, `go generate ./cli`), and logger construction. All of it unexported: configuration is the CLI's operator contract, not library API. `cli/input` reads an input folder: `input.Read(root, mapper, documentSpec)` makes one `folderReader` per call, holding the input root and the violations so far, and reads in two steps. The walk (`walker.go`) looks at names, kinds and places only: the reserved names, the folder rules, and which description files each level has (one at most, and one at the package level). It fills the `build.SourcePackage` as far as the folder's structure does and records in an inventory the files the decoders read. The decoders (`decode.go`) then read those files in the order of the input specification: the sidecar and `representations.csv`, then the description of each level. The content of `description.csv` and `representations.csv` is judged by pure parsers on the file's bytes (`parseTerms`, `parseRepresentationRows`), and the decoders add the file name and line to their findings ([ADR-0023](decisions/0023-cli-input-one-package.md), [ADR-0027](decisions/0027-input-reader-walks-then-decodes.md)). Only the description decoder takes the mapper and the document format; the walk knows only the document's file name. `Read` takes an `input.Mapper`, which maps the rows of `description.csv` onto the profile's description, and an `input.DocumentSpec`, which describes the supplied document by the definition's `DocumentName` and `Model`: when the model implements `build.DocumentFormat`, the name of a supplied document (`dc.xml`, `mods.xml`) is reserved and the model validates its root element; the zero `DocumentSpec` takes none. `cli/input/mapping` holds the profiles' mappings, one type per profile (`Meemoo`, `Eark`, `EarkMods`) implementing that interface; it is the one package under `cli/input` that imports the profile packages, and it does not import `cli/input` itself, so the reader's tests read folders with the real mappings. `cli/profile.go` pairs each profile's name with its mapper.

Dependencies are kept small and boring: cobra (CLI), godotenv + caarlos0/env (config), golang.org/x/text (Unicode path normalization in the input walker); UUIDs come from the Go standard library. No characterization tool is executed and none lives in `go.mod`; format info arrives as a pre-computed report ([ADR-0009](decisions/0009-characterization-as-sidecar-input.md)).

## CLI/library boundary

SIP Creator is a library with a CLI frontend, and the boundary between the two is a design principle the system is converging on. The library is designed to be embeddable in larger systems that automate ingest workflows: systems that hold content as streams (e.g. in object storage) and metadata as structured data, not as operator-prepared directories. The library API is therefore the contract; input formats are frontends that map onto it (the same layering commons-ip uses: a programmatic builder at the core, tools on top).

- **The library owns the domain, not the input.** Its API is the domain model (`sip/`) plus primitives to assemble and emit a package. It never sees a CSV and never assumes a source directory layout.
- **The CLI owns the operator contract.** It reads the input convention (see [input-spec.md](input-spec.md)), merges configuration (agents, profile), enforces the input rules, and translates everything into library API calls. All operator-facing error reporting lives here, in plain language.
- **`build` is the library's face** ([ADR-0019](decisions/0019-build-is-the-library-face.md)): everything a program using the library works with (the source package, the definition, the config, the builder, the metadata model interface a profile implements) lives in `build`. `sip/` holds the shared domain types and the engine's graph, exporting what a template or a second package reads and nothing more; the assembler builds the graph by assigning fields, and the graph's invariants are the assembler's to keep; the graph has no checks of its own.
- **Validation splits in two.** Input-contract errors (bad CSV key, misplaced file, missing folder) are CLI concerns, collected as violations phrased for the operator. Domain invariants are fail-fast `Validate` methods next to the data they guard: `SourcePackage.Validate` (source package rules) and each standard's `Validate` (term validity for Meemoo and eark; for `meemoo` also its cardinality and language rules; for the MODS record its fields and its items), every finding joined into one error. The description rules have one owner: `SourcePackage.Validate` is the contract that runs before any write, the CLI calls the same methods on a rows file to report violations with file and line context, and the metadata models trust the description they are given (the DC templates admit only element names from their tables; the MODS template walks typed fields). What a package-level description must state is each standard's own `ValidateRequired` (an identifier and a title; Meemoo's basic profile also a description and a creation date), which `SourcePackage.Validate` applies at package level and the CLI's `check` calls too, so both commands say the same thing. Any embedding system therefore hits the same guardrails without going through the input convention.
- **The library is converging on streaming input.** The target file-adding primitive takes an `io.Reader` plus a logical path and optional pre-computed fixity, not a source directory: the CLI would feed it opened disk files, an embedding system streams from wherever it stores content. Today essence still arrives as filesystem paths (the known gap below).
- **Characterization is data, not an interface** ([ADR-0009](decisions/0009-characterization-as-sidecar-input.md)): a program using the library supplies a `characterization.Report` directly (`build.SourcePackage.Characterization`); the CLI's `siegfried.json` sidecar file is one transport of the same data. The same strictness (MD5 binding) applies to both.
- **The library is a reference implementation others can use** ([ADR-0022](decisions/0022-reference-implementation-bring-your-own-profile.md)). A profile is something an institution brings: a description type implementing `sip.Description`, a metadata model implementing `build.MetadataModel`, an exported `build.Definition` handed to `build.New`. The registry in `profiles/` is the CLI's list for `--profile`, not the library's limit, and the three in-tree profiles are reference implementations of that route. Where a profile leaves an attribute value to the program that builds the description, the value is a typed constant set that program picks from. Two choices in the eark profiles are RODA's, not E-ARK's: they emit no PREMIS, because RODA drops package PREMIS that describes no agents or events, and they carry the representation type in the content typing, because RODA reads it there ([ADR-0013](decisions/0013-representation-type-from-label.md)). They stay until a consumer that wants otherwise appears.

**Known gap:** the builder takes its source package as data (`build.SourcePackage`: descriptive terms, representations as source paths, documentation, received PREMIS, a characterization report, an optional package identifier), so systems that keep their content elsewhere construct its input without the folder convention. But essence still arrives as filesystem paths, not streams, and fixity cannot yet be supplied pre-computed. The remaining work (streams and pre-computed fixity) is tracked in [TODO.md](TODO.md).

## Input contract

The CLI's input contract is the convention-based folder defined in [input-spec.md](input-spec.md), the authoritative, operator-facing statement of every rule. In brief: one folder is one package, carrying one description per level: the rows file `description.csv`, as key–value terms in the keys of the profile passed to `check` and `create`, or, under the eark profiles, a finished `dc.xml` or `mods.xml` in its place (the key table per [ADR-0011](decisions/0011-closed-descriptive-vocabulary.md), the profile deciding it per [ADR-0016](decisions/0016-descriptive-input-rows-or-supplied-document.md), the document per [ADR-0021](decisions/0021-descriptive-model-follows-its-standard.md); `input.Read` takes an `input.Mapper`, the one-method interface that maps the decoded terms onto the profile's description and reports each term it cannot place, and an `input.DocumentSpec`, the definition's document name and metadata model, which names the document's file and validates its root element as the engine will, so `cli/input` imports no profile package and takes no profile definition; the mappings live beside it in `cli/input/mapping`, one per profile, each importing its profile package), content either flat or under `representations/<name>/`, and optional `representations.csv` (a per-representation label and type, strict when present: every row must match a representation folder and every folder must be covered, [ADR-0014](decisions/0014-representations-csv-strict-when-present.md)), `documentation/`, `premis/` (received preservation XML, passed through unparsed) and a `siegfried.json` characterization sidecar ([ADR-0009](decisions/0009-characterization-as-sidecar-input.md)). Administrative values come from configuration, not the folder ([ADR-0010](decisions/0010-config-over-self-describing-input.md)).

`cli/input` enforces the contract, collecting every MUST violation into one report phrased for the operator; the `check` command runs that validation standalone. The same rules that hold for the *graph* rather than the folder (descriptive validity, identity and requiredness, received-PREMIS conformance, characterization checksum verification) are enforced again in the builder for every producer: the folder is one transport onto `build.SourcePackage`, not the API.

`examples/basic/`, `examples/eark/` and `examples/eark-mods/` are the sample inputs, tracked in git and built by a Go test in `cli/` (`TestExamplesBuild`). `build.sh` copies one to `tmp/build/<profile>` and builds from the copy, because it writes `siegfried.json` next to the input. `<profile>-uuid/` is the generated output, and `tmp/reference/` holds the reference copy of each profile's package that `scripts/reference-diff.sh` compares against; both are local, not tracked in git.

## Validation

The acceptance check is **external**: generated packages are validated with commons-ip, the E-ARK CSIP reference validator. The CSIP rules are *not* reimplemented as Go tests; commons-ip is the reference (see [ADR-0003](decisions/0003-validation-stays-external.md)). Go tests cover what the validator can't see: the `store/` primitives (fixity, truncation on rewrite, fail-fast), the engine (`build/`: graph shape, meemoo-layer semantics like `MEEMOO-LOCAL-ID`, the guarantee that assembly writes nothing to disk, and the supplied-document route: a document of the profile's standard lands as it is with fixity and the declared typing, while another standard's, another MODS version's, a malformed or missing file and any document under `basic` are refused before any write), the input reader (`cli/input`: folder walk, CSV decoding, violation collection, and the supplied-document rules: one description per level, the document's name reserved only under a profile that takes one, a malformed file or another standard's root reported with the file name, and a folder's document building with the real eark profile) and the profiles' mappings for it (`cli/input/mapping`: eark's terms keep their order, Meemoo's keys become their elements in order with an unknown key refused at its index, every element the Meemoo mapping names is one the library accepts, and a term the MODS mapping cannot place is an error at its index, reported at its line; `cli/`: every registered profile has a mapping whose description its metadata model accepts, and every example folder builds), the profile packages' description models (`profiles/meemoo`, `profiles/eark`, `profiles/earkmods`, each pinning its required list against its table), the received-PREMIS check (`encoders/premis`) and the XML root reader under it (`encoders/xmldoc`), the METS dmdSec typing (`encoders/mets`), the schema lists, and the registry (`profiles/`: every listed schema is bundled, every entry names a metadata model, and each profile's descriptive document hints only at schema files its model lists, so the template and `Schemas()` cannot drift apart).

The workflow around the tool ([ADR-0005](decisions/0005-dockerized-validation-and-html-reporting.md)): `./build.sh [profile]` is the local CI loop: build, regenerate the sample SIP, validate the zip with a dockerized commons-ip (release jar pinned by version + sha256), and exit non-zero iff the package is not `VALID` (the commons-ip CLI itself always exits 0; the verdict is read from its JSON report). The spec version is pinned per profile's era: `basic`/meemoo-1.2 against 2.0.4 (whose profile URL Meemoo 1.2 requires), `eark` and `eark-mods` against 2.2.0. A commons-ip default change therefore can't silently move the goalposts. commons-ip checks the METS, not the descriptive documents it points at, and a supplied `mods.xml` is copied as it is, so the script also validates every `mods.xml` in the package with xmllint against the MODS 3.7 schema the package ships, offline through the XML catalog `scripts/schema-catalog.xml` (which maps the two loc.gov URLs the schema imports onto the bundled copies), and an invalid document fails the run like an INVALID package. Each run's reports are published to `reports/runs/<timestamp>-<profile>/`; `docker compose up -d reports` serves a static HTML view of all runs at http://localhost:8080. `scripts/validate.sh` is usable standalone against any package zip or directory.

## Known gaps

These are true of the code today and tracked in [TODO.md](TODO.md):

- **The `sip.Event` stub is unused.** PREMIS events are not modeled; the stub anchors the events design question in [TODO.md](TODO.md). (The once-unused `sip.Identifier` interface was deleted 2026-08-20; identifiers are plain `uuid-<uuid>` strings, validated by `sip.ValidateIdentifier`.)
- **Essence arrives as filesystem paths, not streams**, and fixity cannot be supplied pre-computed; this is the remaining embeddability work (see the CLI/library boundary above).

Resolved 2026-08-20 with the [input-convention plan](archive/input-convention.md): `mets/@TYPE` is operator-selectable (`--content-category`, `SIP_CONTENT_CATEGORY`), and the old `representation_N` input regex is gone: operator folders under `representations/` are free-form labels. Since 2026-09-01 the label also names the package-side directory verbatim (before that, the assembler renamed to `representation_N`).

The [refactoring plan](archive/refactoring-plan.md) and its companions have shipped: the assemble/emit split, `store/` package, and declarative `Definition` registry (Phases 0–2), the decision to make enrichment optional ([format-identification plan](archive/format-identification-optional.md), since superseded in part), and the eark profile ([eark-writer plan](plans/eark-writer.md), awaiting field acceptance on RODA). The [characterization-sidecar plan](archive/characterization-sidecar.md) has landed in full: Step A (sidecar input) and Step B (METS `@MIMETYPE` emitted from resolved per-file mime; the long-standing hardcoded-`text/xml` lie is gone). The [descriptive-model plan](archive/descriptive-model.md) shipped on 2026-10-01 ([ADR-0021](decisions/0021-descriptive-model-follows-its-standard.md)): the descriptive model follows its standard, the CLI's mappings own the CSV's keys, a supplied `dc.xml` or `mods.xml` is a second description type for the eark profiles in both the library and the folder, and the eark-mods profile has its fixture, its reference copy and the xmllint pass in build.sh.
